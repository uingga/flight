## 이전 파일럿 절차 (운영 전환 전 기록)

## 목적

GitHub 실행 환경에서 땡처리닷컴 접근 제한이 확인됐을 때, 다른 Windows PC의 일반 Chrome
네트워크와 독립 프로필을 사용해 해당 소스만 안전하게 검증한다. 초기 운영은 결과를 곧바로
배포하지 않고 staging 파일과 변경 요약만 만든다.

## chacha95/automation에서 유지한 의도

- 평소 Chrome 사용자 데이터에서 한 번 준비한 별도 프로필을 계속 재사용한다.
- 원래 Chrome과 충돌하지 않는 로컬 디버그 포트(`127.0.0.1:9222`)를 사용한다.
- 사람이 브라우저 상태를 볼 수 있는 일반 Chrome을 실행한다.
- Playwright는 새 브라우저를 가장하지 않고 이미 열린 Chrome에 CDP로 연결한다.

사이트를 속이기 위한 `AutomationControlled` 관련 플래그, 매 실행 프로필 재복사, 개인 Chrome
프로필에 직접 연결하는 방식은 사용하지 않는다. Google 로그인이 복제되지 않아도 땡처리닷컴
수집에는 필요하지 않으므로 로그인을 강제하지 않는다.

## 현재 실행 방법

다른 PC의 저장소에서 의존성을 설치한 뒤 다음 명령 하나를 실행한다.

```bash
npm run crawl:ttang:browser:pilot
```

이 명령은 다음 순서로 동작한다.

1. 기존 `~/tmp/chrome-debug` 프로필과 Chrome 설치 여부를 확인한다.
2. 필요한 경우 최소 플래그로 보이는 Chrome을 실행한다.
3. 운영 `data/`를 `.local-crawler/staging/ttang-<시각>/`에 복사한다.
4. 복사본만 대상으로 땡처리 목록과 상세를 수집한다.
5. `summary.json`과 검토용 `all-flights-cache.json`을 남긴다.

운영 `data/all-flights-cache.json`, Git 브랜치, 원격 저장소는 변경하지 않는다.

GitHub 땡처리 회로가 실제로 열린 경우만 확인하는 예약용 명령은 다음과 같다.

```bash
npm run crawl:ttang:browser:scheduled
```

이 명령은 기존 `local-source-fallback-policy.mjs`가 현재 회차의 땡처리 대체 수집을 허용할 때만
Chrome과 staging 수집기를 실행한다. 실행 전 다른 PC의 저장소가 최신 `main`을 받은 상태여야 한다.

## 상품 식별과 요청량

- 목록 카드의 `masterId`, `hanaFareId`, `gubun`, `tktCar`를 함께 저장한다.
- 같은 노선·날짜·항공사라도 `hanaFareId`가 다르면 다른 요금 상품으로 취급한다.
- 목록은 한 번 연 페이지 안에서 날짜별 API를 호출한다.
- 상세는 최종 필터를 통과한 신규·재확인 대상 중 최대 20개만 조회한다.
- 상품당 `scheduleAct.do` 한 번으로 시간과 좌석을 함께 확인한다. 요청에는 실제 화면과 같은
  `fareType`·노선·날짜·항공사 값을 넣고, 목록의 `hanaFareId`는 `fareRec1`으로 전달한다.
- 상세 요청 사이는 4~8초, 10건 뒤에는 30~60초를 추가로 쉰다. 오류가 이어지면
  4~6.4초부터 최대 30~48초까지 대기 시간을 단계적으로 늘린다.
- 401·403·429·CAPTCHA는 첫 응답에서 즉시 중단한다. 같은 API 오류 코드나 응답 형식 오류는
  3건 연속, 일시 오류 또는 혼합 오류는 최대 8건 연속이면 남은 요청을 중단한다.

## 중간 실패 시 상세 성공분 보존 (staging 전용)

- staging 실행기는 고유 `runId`와 시작 시각을 전달하고, 상세 조회 단계가 시작되면
  `ttang-detail-checkpoint.json`을 만든다. 기존 실행 폴더/체크포인트는 덮어쓰지 않는다.
- 실제 상품 상세 요청에서 성공한 결과만 `successes`에 기록한다. 상품번호(`masterId`) +
  운임번호(`fareId`) + 출발일이 선택한 상품과 정확히 같아야 하며, 노선·항공사·귀국일도 보존한다.
  현재 실행에서 확인한 시각, 어댑터 버전, 유효한 시간 네 개가 필수다.
- 성공 패치는 시간·좌석만 갖는다. 과거 캐시의 가격·비교가·시간을 통째로 복사하지 않는다.
  새 좌석이 0/없음이면 `seatAction: clear`로 기록해 과거 양수 좌석을 재사용하지 않는다.
- 정상 빈 결과와 실패는 `outcomes`에만 남는다. 미조회·이월과 상품 상세로 확인하지 않은
  과거 노선 기반 조회(`excludedLegacy`)도 별도 집계하고 성공분에 넣지 않는다.
- 각 상품 요청 직전과 응답 직후, 동기 쓰기 → 파일 flush → 원자적 rename으로 체크포인트를
  갱신한다. 프로세스 강제 종료 시 마지막 저장분은 남지만 진행 중이던 요청의 성공은 추정하지 않는다.
- `summary.json.partialDetails`에는 성공·빈 결과·실패·미조회 수, 마지막 완료 키와 진행 중 키,
  중단 사유를 남긴다. 자식 프로세스가 끝났는데 체크포인트가 `running`이면 `interrupted`로 보고한다.
  파일이 깨졌거나 실행 ID/집계가 맞지 않으면 `invalid`이며 검증에 통과시키지 않는다.
- 검증 건수는 현재 `runId`·시작 시각·어댑터에 속한 체크포인트 성공 패치/성공 outcome과
  상품 식별·노선·확인 시각·시간 네 개·좌석 설정/삭제가 정확히 일치하는 항공권만 센다.
  과거 캐시 값만 있거나 확인 시각이 미래이면 승인 근거로 사용하지 않는다.
- 중단된 회차의 일부 성공이 있어도 `ready_for_review`로 승격하지 않는다. 상세 실패가 남은
  완료 회차도 staging 승인에서 제외한다. legacy 실패는 상품 `failed` 집계에 없고 완전한
  상품 성공 증거도 없으므로, staging은 보수적으로 `excludedLegacy > 0`인 회차를 모두 제외한다.
  `completed`는 상세 단계 종료이지 전체 수집·운영 성공이 아니다.
- **자동 병합 기능은 없다.** 중단 시 기존 항공권·`sourceUpdatedAt`·보강 상태 복원,
  실패 횟수와 차단 회로 처리 방식은 그대로 유지한다. 체크포인트는 검토용 증거이며 모든 파일에
  `operationalEligible: false`를 기록한다. 운영 병합은 별도 설계·검증·승인이 필요하다.
- Windows의 일시적인 교체 잠금(`EPERM`·`EACCES`·`EBUSY`)은 같은 임시 파일의 rename만
  최대 6회 재시도한다(총 대기 2.55초). 사이트 요청은 반복하지 않으며 기존 체크포인트를
  먼저 지우거나 직접 덮어쓰지 않는다. 임시 파일명은 매번 고유하며 실패 파일은 증거로 남긴다.
- 잠금 재시도 소진 또는 다른 저장 오류는 추가 요청 없이 중단한다. 차단 응답과 저장 오류가 함께 발생하면 원래 차단 오류를
  우선 전달해 기존 차단 회로가 누락되지 않게 한다. 디스크 자체가 고장 나면 최신 응답 저장은
  보장할 수 없으며 이전에 정상 저장한 체크포인트까지만 남는다.
- 허용 위치는 실제 경로 기준 `.local-crawler/staging/` 아래의 개별 실행 폴더다.
  운영 `data/`나 그곳을 가리키는 junction/symlink에는 체크포인트를 쓰지 않는다.
- 기본 실행은 상세 **20개·30분**을 유지한다. 사용자 승인 후 수동 1회 전체 검증은
  `npm run crawl:ttang:browser:pilot -- --all-details`를 사용한다.
  이 모드만 **전체 조회 적격 후보·60분**을 적용하며, 재확인 대기 정책과 요청 간격은 유지한다.
  `ttang` 단독 staging·체크포인트가 필수이고 예약 fallback과 함께 사용할 수 없다.
  운영 데이터 반영·자동 재실행은 하지 않는다.

오프라인 검증: `npm run test:ttang-partial`, `npm run test:ttang-staging`.
테스트는 가짜 브라우저 응답·임시 디렉터리·실제 자식 프로세스 종료를 사용하며 사이트에 요청하지 않는다.

## 자동 운영 전 확인 순서

1. 수동 staging 실행 한 번으로 `productIdentified`, `timeVerified`, `seatVerified`를 확인한다.
   `timeVerified`와 `seatVerified`가 각각 한 건 이상이어야 `ready_for_review`로 통과한다.
2. 선택한 항공권 한 건의 시간·좌석·가격을 실제 화면과 대조한다.
3. 최소 여러 회차 동안 운영 데이터와 staging 결과를 비교한다.
4. 검증 전에는 자동 병합·커밋·푸시를 추가하지 않는다.
5. 안정화 뒤에도 예약 작업은 먼저 GitHub 회차 상태를 확인하고, 땡처리 회로가 열린 경우에만
   이 수집기를 호출하도록 구성한다.

## 전용 B PC 실행과 검증 범위 (2026-09-06)

실행기는 PowerShell 없이 Node.js가 전용 프로필의 보이는 Chrome을 시작한다. 기존
`hermes:ttang:*` 명령은 호환용 실행기 이름이며 Codex에서도 같은 npm 명령을 사용할 수 있다.
호스트 등록·동시 실행 잠금·운영 파일 해시 대조를 사용하는 실행 방법은
`docs/hermes-remote-crawler.md`의 기존 실행자 절차를 참고한다. 새 원격 연결이나 스케줄은
이번 통합에서 설정하지 않았다. `hermes:ttang:pilot -- --all-details`도 명시적 파일럿에만
전체 적격 후보 옵션을 전달하며 예약 실행은 이 옵션을 거절한다.

기본 파일럿과 예약 fallback은 상세 최대 20개·30분, 명시적 전체 파일럿만 60분이다.
전체란 원본 모든 상품이 아니라 최종 필터와 재확인 대기 정책을 통과한 적격 후보 전부다.
기준가 캐시가 없더라도 부분 수집 중 인터파크에 새 요청을 보내지 않는다.

정상 종료 시 이 회차의 탭과 CDP 연결을 정리한다. 외부 Chrome 자체의 강제 종료는 보장하지
않으며, 시간 제한·프로세스 강제 종료 뒤 전용 PC에서 브라우저/프로세스 상태를 확인해야 한다.
새 요약이 없는 실패를 이전 회차의 성공 요약으로 표시하지 않는다.

2026-09-05 상세 97개 성공이라는 인수인계는 자기 보고다. 해당 원본 staging이 원격 Git에
없어 이번 오프라인 통합에서 독립 검증하지 않았다. 원본 확보 후 runId·체크포인트·요약·실제
화면을 대조하고, B PC에서 승인된 단일 파일럿을 검증한 뒤 운영 병합을 별도로 결정한다.
이번 변경은 실수집·운영 병합·스케줄 전환·push·배포를 수행하지 않는다.
