# 유입처 진단 — 2026-09-09

## 확인된 사실

- 사용자가 기존 GA4 읽기 전용 서비스 계정 사용을 승인한 뒤 Data API를 조회했다. 인증 파일을 복사하거나 인증값을 출력하지 않았고, 운영 설정·이벤트·원본 데이터는 변경하지 않았다.
- 2026-09-03~09-08의 네이버 검색은 `naver`, `m.search.naver.com`으로 나뉘어 있었다. 정확한 필터 합집합으로 조회한 결과 12세션·11명이다. 블로그는 `naver_blog`, `m.blog.naver.com`이며 합집합 결과 3세션·3명이다. Keep은 별도 서비스로 유지한다.
- 여행사 코드가 GA4 `sessionSource` 및 `sessionManualSource`에 실제로 기록되어 있고 medium은 주로 `(not set)`이다. 해당 세션의 최초 유입에는 네이버·TE31·직접 방문이 있고, 조회한 referrer에는 여행사 도메인이 없었다. 내부 여행사 코드를 여행사에서 온 방문으로 해석할 근거는 없다.
- 과거 `detail_open`, `city_detail_open`은 여행사 코드를 일반 `source` 이벤트 속성으로 보냈다. 8304e6cb에서 `travel_agency`로 변경됐다.

## 인과관계의 한계

- 현재 공개 Google 태그로 과거 `source` 필드와 `?source=hanatour` URL을 재현했다. 수집 요청을 모두 차단한 상태에서 `ep.source` 및 `dl`에는 값이 있으나 `cs`는 확인되지 않았다. 과거 이벤트 필드가 실제 세션 유입처를 덮어썼다는 인과관계까지 확정한 것은 아니다.
- GA4 Admin API는 프로젝트에서 비활성화되어 수정 규칙을 읽지 못했다. 브라우저 관리 화면도 로그인이 필요했다. API 활성화·권한 추가·로그인 정보 탐색은 하지 않았다.
- 최초 유입처를 현재 세션의 원래 유입처로 대입하지 않는다. 실제 유입처가 확인되지 않은 과거 기록을 추정해서 복구하지 않는다.

## 구현한 처리

- 알려진 출처 별칭을 서비스별로 묶고, GA4의 정확한 채널·출처·medium 합집합을 조회해 세션·인원의 중복을 제거한다. 원본 출처 목록은 보존하며 합집합 집계 실패 시 임의 합산하지 않는다.
- 내부 여행사 코드만 출처 순위에서 분리해 `출처 확인이 필요한 기록`으로 보관한다. 실제 여행사 도메인은 분리 대상이 아니며, 방문·행동 원본 및 전체 지표를 삭제하거나 차감하지 않는다.
- 공통 이벤트 전송 함수에서 여행사 코드가 `source` 또는 `campaign_source`로 들어오면 `travel_agency`로 옮긴다. 정상 캠페인 출처는 유지한다.
- 직접 방문은 주소 입력·북마크 외에도 출처가 전달되지 않은 앱·메신저 방문 등을 포함한다고 설명한다. `(not set)`과는 구분한다.

## 검증

- 기존 집계 회귀, 별칭 합집합·실패 처리, 여행사 코드 분리 시 원본 보존, 공통 이벤트 방어 및 소유자 제외 테스트.
- 뒤로가기 후 상세·예약 이벤트가 여행사 코드를 유입 출처로 전송하지 않는 브라우저 테스트. 실제 Google Analytics에는 테스트 요청을 보내지 않았다.
- 실제 완료 기간 Data API로 통합 집계와 기록 분리 확인. 프로덕션 빌드 및 PC·모바일 화면 검증은 배포 전 수행한다.
