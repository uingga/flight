# 여행사 크롤링 안전장치

2026-08-31 운영 기준이다. 목표는 차단을 우회해 요청을 계속하는 것이 아니라, 차단 징후가
나오면 남은 요청을 중단하고 이전 정상 데이터를 보존하는 것이다.

## 공통 운영

- 일반 여행사 5곳은 KST 08:17, 11:12, 14:23, 17:31 하루 4회 실행한다.
- 워크플로 시작은 0~5분, 여행사별 시작은 최대 90초 무작위로 분산한다.
- 401·403·429·CAPTCHA·WAF 문구는 명시적 제한으로 처리한다.
- 원본 0건 또는 직전 정상 원본의 60% 미만이면 HTTP 200이어도 soft block으로 처리한다.
- 제한이 확인된 소스만 24시간 쉬며, 이전 항공권·원본 기준선·갱신 시각은 유지한다.
- 차단 회로 때문에 요청하지 않은 회차는 `건너뜀`으로 기록하고 실제 실패 횟수에 더하지 않는다.
  이때 차단 회로의 `nextProbeAt`을 함께 저장해 어드민에 언제까지 건너뛰는지 표시하고, 그 시각이
  지난 뒤 첫 정규 회차에서 1회 재탐색한다. 어드민 그래프에서도 실패와 다른 회색 표식으로
  표시하며 수집량 평균에서 제외한다. 과거 기록에 종료 시각이 없으면 임의로 추정하지 않는다.
- 전체 결과가 이전 캐시의 50% 미만이어도 차단 회로와 실패 메타데이터는 별도로 저장한다.
  완료 표식을 남겨 watchdog이 같은 예약 회차를 다시 실행하지 않게 한다.
- GitHub에서 쉬는 일반 여행사는 Windows PC가 그 소스만 대체한다. 단, 모두투어는 PC 자동
  접속 대상에서 제외하고 어드민에 수동 캡처 필요 상태를 표시한다. 나머지 소스의 PC 차단은
  소스별 24시간이다.

## 소스별 추가 보호

- 노랑풍선: 지역 탭 누락을 먼저 검증한다. 상세 시간 POST는 노선별 최저가·만료·편도·인터파크
  필터를 모두 통과해 실제 노출될 항공권에만 실행하고, 한 번도 조회하지 않은 후보부터 회차당
  최대 40건을 처리한다. 성공값과 마지막 시도 상태는 `all-flights-cache.json`의
  `ybtourTimeEnrichment`에 저장한다. 일시 오류는 2시간 뒤, 응답 형식 불일치는 처음 3일 뒤와
  반복 시 7일 뒤부터 다시 확인하고 어댑터 변경 항목을 우선 재검증한다. 요청 사이 1~1.8초,
  20건마다 10~20초 쉬며 연속 요청 실패 8건이나 401·403·429·CAPTCHA는 `ybtour` 소스
  차단으로 처리한다. GitHub의 `ybtour`만 쉬고 PC가 `--sources=ybtour`로 대체하며, PC에서도
  차단되면 PC의 `ybtour` 대체 수집만 24시간 중단한다.
- 하나투어: 출발 탭별 3~5초 휴식, CAPTCHA 재검사, 카드 출발 공항과 선택한 탭을 대조해
  직전 탭의 stale DOM을 거부하고 모든 탭 예외를 불완전 수집으로 기록한다. 왕복 카드의
  가는편·오는편 행에서 출발·도착 네 시각을 각각 읽으며, 일부 시각이 없으면 추정해 채우지 않는다.
- 모두투어: GitHub 정규 수집은 초기 페이지와 6개 대륙 API에 20초 제한, 네트워크·5xx만
  최대 1회 재시도하고 JSON content-type과 `result` 배열을 검증한다. GitHub에서 명시적
  차단 회로가 열리면 현재 PC를 포함한 자동 대체 수집은 모두투어에 접속하지 않는다. 운영자가
  일반 Chrome에서 결과 화면을 확인하고 캡처를 전달하면, 날짜·노선·시간·가격·좌석·할인율을
  검증한 확실한 카드만 반영한다. 처음부터 끝까지 완전 캡처된 지역은 0건 결과까지 포함해 이번
  캡처 결과로 교체하고, 일부만 캡처된 지역은 기존 데이터에 추가·갱신만 한다. 캡처하지 않은
  지역과 판독이 애매한 카드는 운영자 확인 전까지 건드리지 않는다. 수동 카드가 생기면 네이버
  확인 대기로 표시해 11:12 이전은 1차, 14:23 이전은 2차, 17:31 이전은 3차에 모두투어만
  확인한다. 17:31 이후 반영분과 하루 200회 한도 뒤 남은 항목은 다음 날 1차로 넘긴다.
  수동 캡처의 반영 시각·확정 수·지역 상태는 다음 자동 회차에도 보존하며, 모두투어 자동 수집이
  실제로 성공했을 때만 수동 상태를 닫는다.
  검수에 성공한 수동 캡처는 자동 회차와 별도의 영구 수집 기록으로 남겨 어드민 그래프에 청록색으로 표시한다.
  앞선 회차에서 403·429·CAPTCHA가 확인된 날은 수동 캡처 3차도 실행하지 않는다.
- 온라인투어: 요청 20초 제한, 네트워크·5xx는 3초 뒤 한 번만 재시도, JSONP·페이지 총수·ID 중복 검증.
  페이지 사이는 2~4초, 지역 사이는 3~5초 쉬고 목록 변동으로 지역 전체를 다시 읽기 전에는 8~15초 쉰다.
- 땡처리닷컴: 브라우저 쿠키 세션으로 날짜 API를 직렬 조회하고 1.2~2.4초 간격,
  5일마다 3~6초 추가 휴식. 네트워크·5xx 재시도도 3초 뒤 한 번만 허용한다.
  8일 연속 빈 날짜 응답이나 12일 표본 성공률 20% 미만이면 즉시 중단한다. 시간 보강은
  노선별 최저가·만료·편도·인터파크 필터를 모두 통과해 실제 노출될 항공권에만 실행하며,
  회차당 실시간 페이지 이동은 최대 20개 노선이다. 한 번도 조회하지 않은 신규 항공권을 먼저
  처리하고 기존 성공 시간은 재사용한다. 일시 오류는 2시간 뒤, 빈 결과는 3일 뒤부터 다시 보고
  반복 빈 결과는 7일 간격으로 늦춘다. 항공사·응답 형식 불일치는 어댑터 버전이 바뀔 때만 다시
  확인한다. 성공값과 마지막 시도 상태는 `all-flights-cache.json`의 `ttangTimeEnrichment`에
  저장해 필터에서 잠시 빠졌다 돌아온 표도 다시 조회하지 않는다. 실시간 보강 8건 연속 실패나
  401·403·429·CAPTCHA는 `ttang` 소스 차단으로 처리한다. GitHub의 `ttang`만 24시간 쉬고
  기존 데이터를 유지하며, Windows PC는 다음 정규 회차에 `--sources=ttang`만 대체 수집한다.
  PC에서도 차단되면 PC의 `ttang` 대체 수집만 24시간 중단한다.
- 마이리얼트립: 공개 API 20초 제한과 응답 구조 검증, Calendar 요청 0.8~1.6초 간격.
  원래 비어 있는 개별 출발지는 허용하고, 모든 출발지가 0건이거나 기존에 데이터가 있던
  출발지만 사라지면 실제 예약 페이지를 열기 전에 중단해 기존 캐시를 보존한다.
  Playwright는 워커 1개, 노선 사이 4~8초, 10건마다 30~60초 휴식한다. 실제 운임 8건 연속
  실패 또는 20건 표본 성공률 20% 미만이면 즉시 중단하고 24시간 회로를 커밋한다.
- 인터파크 벤치마크: 24시간 캐시를 재사용하고, 갱신일에도 전체 도시를 다시 묻지 않는다.
  기존 월평균가는 보존한 채 미수집 도시 또는 가장 오래 확인하지 않은 도시를 하루 최대 25개만
  순환 갱신한다. 도시 요청 사이는 1.2~2.4초, 10건마다 8~15초 더 쉬며, 인기 도시 묶음 최저가는
  마지막에 1회만 요청한다. 401·403·429·CAPTCHA는 즉시, 일반 오류 또는 기존 도시의 빈 응답은
  3건 연속이면 남은 도시와 인기 도시 요청을 중단한다.

## 데이터 채택 기준

- 지역·탭·날짜 일부가 실패하면 해당 소스의 이번 결과 전체를 폐기한다.
- 일반 소스 원본이 직전의 60% 미만이면 폐기한다. 85% 미만이면 항공권 소멸 판정에는 쓰지 않는다.
- 전체 노출 결과가 직전의 50% 미만이면 이전 전체 캐시를 유지한다.
- 마이리얼트립 실제 운임 성공률이 50% 미만이면 이번 결과를 저장하지 않는다.
