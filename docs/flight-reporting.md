# 항공권 정보 신고 운영 방식

상세 화면의 `가격이 달라요`, `예약이 안 돼요` 버튼은 신고를 저장하고,
서로 다른 신고가 모이면 해당 항공권을 목록에서 잠시 숨긴다.

## 사용자가 버튼을 누르면

1. 배포된 캐시에 실제로 존재하는 항공권인지 서버가 다시 확인한다.
2. 신고를 Supabase `flight_reports`에 저장한다.
   상태가 바뀔 때마다 `flight_report_events`에도 이전 기록을 덮어쓰지 않고 한 줄씩 쌓는다.
3. 운영자 이메일로 신고 번호와 항공권 정보를 보낸다. 세 번째 유효 신고면 임시 숨김 사실도 알린다.
4. 브라우저에는 하루 동안 `신고 접수 완료`를 유지한다.

같은 접속자가 같은 항공권을 반복해서 눌러도 24시간 동안 DB 행과 이메일은
한 번만 만들어진다. 브라우저에서도 성공 후 24시간 동안 다시 전송하지 않는다.
서로 다른 항공권은 10분에 최대 5건까지 신고할 수 있다.

신고자의 실제 IP는 저장하지 않는다. service-role 키로 만든 되돌릴 수 없는 식별값만 저장한다.

## 세 건 신고 임시 숨김

신고 때문에 여행사를 추가 크롤링하지 않는다. 24시간 안에 서로 다른 익명 기기 3개와
접속망 2곳 이상에서 같은 항공권을 신고하면 `flight_report_hides`에 기록하고 24시간 숨긴다.
한 여행사에서 자동으로 숨길 수 있는 항공권은 하루 최대 5개다.

신고 처리 기준:

- 한두 건은 신고 기록과 이메일만 남긴다.
- 세 번째 유효 신고가 들어오면 캐시 파일을 삭제하거나 고치지 않고 API 목록에서만 숨긴다.
- 관리자는 `/admin`의 `항공권 신고` 탭에서 `계속 숨김` 또는 `다시 표시`를 고를 수 있다.
- 관리자가 결정하지 않으면 24시간 뒤 자동으로 다시 표시한다.
- 15분 자동 재확인 워크플로는 예약 실행하지 않는다. 꼭 필요할 때만 관리자가 수동 실행한다.

`flight_report_events`에는 신고 접수, 임시 숨김, 자동 해제, 관리자 숨김·해제와
수동 확인을 실행했을 때의 가격 갱신·판매 종료·확인 실패를 시간순으로 기록한다.
따라서 현재 상태가 나중에 다시 바뀌더라도 앞선 처리 기록은 사라지지 않는다.

## 처리 상태

- `pending`: 신고 기록됨. 자동 크롤링을 기다린다는 뜻은 아니다.
- `processing`: 관리자가 수동 확인을 실행한 경우 확인 중
- `confirmed`: 표시 정보와 여행사 결과가 같음
- `updated`: 수동 확인에서 가격 또는 항공편 정보 수정
- `removed`: 판매 종료가 확인되어 목록에서 제거
- `check_failed`: 세 번 확인했지만 여행사 응답을 신뢰할 수 없어 기존 표 유지

현재 상태 테이블 정의는 `supabase/migrations/20260821_create_flight_reports.sql`,
변경 기록은 `supabase/migrations/20260821_create_flight_report_events.sql`, 임시 숨김은
`supabase/migrations/20260821_create_flight_report_hides.sql`에 있다.
RLS를 켜고 공개 클라이언트 권한을 제거했으므로 Vercel API와 GitHub Actions의
`SUPABASE_SERVICE_ROLE_KEY`만 읽고 쓸 수 있다.
