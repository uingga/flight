## 데이터 흐름

```text
여행사별 수집
→ 소스별 완결성·차단 검사
→ 기존 정상 데이터 보존 또는 새 데이터 채택
→ 노선·날짜·가격·유효성 필터
→ 인터파크·네이버·과거 가격 근거 결합
→ data/all-flights-cache.json
→ API와 운영 메인
```

수집 성공과 웹사이트 노출은 같은 숫자가 아니다.

- 원본 수집 수: 여행사에서 읽은 카드·상품 수
- 고유 상품 수: 상품 식별자로 중복을 나눈 수
- 필터 통과 수: 날짜·왕복·가격·기준가 등 운영 조건을 통과한 수
- 현재 노출 수: 기존 보존 데이터까지 포함해 사이트에 실제 나가는 수
- 관측 횟수: 같은 상품을 여러 회차에서 본 횟수

상태를 보고할 때 이 숫자들을 섞지 않는다.

## 소스 실패의 공통 원칙

- 401·403·429·CAPTCHA, 원본 0건, 비정상 급감은 수집 성공으로 처리하지 않는다.
- 실패한 소스의 기존 정상 항공권은 보존하고, 실패 시각 때문에 항공권 정보가 새로 확인된 것처럼 갱신하지 않는다.
- 보존된 데이터와 이번 회차 새로 수집한 데이터를 어드민에서 구분한다.
- 접근 제한이 감지되면 같은 날 억지 재시도하거나 다른 요청 방식으로 우회하지 않는다.
- 일부 단계가 실패했을 때 전체 캐시를 오래된 결과로 덮어쓰지 않는다.

## 여행사별 중요 상태

### 모두투어

- 중국은 `전체` 한 번으로 받지 않고 화면에 노출되는 10개 도착 도시를 개별 확인한다.
- 기존 데이터가 있던 도시 하나라도 실패하면 불완전한 중국 결과를 채택하지 않고 이전 모두투어 데이터를 보존한다.
- GitHub 실패 뒤 PC에서 자동 접속하지 않는다.
- 운영자가 일반 Chrome 화면을 캡처하면 검증된 카드만 수동 반영한다.

### 땡처리닷컴

- 일반 GitHub 수집은 하루 두 번만 한다.
- 상세 시간 보강은 최종 노출 필터 뒤 신규 미확인 항공권부터 회차당 최대 20개 노선을 확인한다.
- 새 브라우저 수집기는 보이는 Chrome과 전용 프로필을 사용하고 결과를 staging에만 남긴다.
- 브라우저 수집의 목록 카드에서는 `masterId`, `hanaFareId`, 최소 예약 인원, 가격과 일정을 읽을 수 있다.
- 실제 상품을 구분하는 데 `hanaFareId`가 필요하다. 같은 `masterId`에 여러 요금이 있을 수 있다.
- 시간·좌석·편명은 `scheduleAct.do`의 해당 `hanaFareId` 응답에서 함께 확인할 수 있다는 수동 조사 결과가 있다.
- `minimumCnt`는 최소 출발 인원이 아니라 한 번에 예약해야 하는 최소 인원으로 취급한다.

2026-09-04 마지막 공유된 파일럿에서는 목록 1,282건을 읽었지만 상세 응답이 `code=E001`,
빈 배열로 와 검증에 실패했고 기존 138개가 보존됐다. 이후 브랜치에 종료 처리·상세 흐름·파일럿 상한
수정이 들어갔지만, 운영 병합 전 최신 코드로 종단간 파일럿 성공을 다시 확인해야 한다.

### 마이리얼트립

- 일반 `crawl-all.ts`에서는 실행하지 않는다.
- 07:05, 16:03 별도 회차에서 실시간 예약 페이지의 가격·시간을 확인한다.
- 각 회차 직전에 인터파크 `빠르게 떠나는 최저가 해외항공`을 새로 읽어 추가 날짜 후보로만 사용한다.
- 빠른 출발 목록은 월별 기준가에 섞거나 과거 회차에서 재사용하지 않는다.
- 보조 후보 실패는 정규 수집 실패율에 넣지 않는다.

### 인터파크

- 월별 기준가는 `출발 권역|도착 도시` 단위다.
- 인천·김포는 `SEL`, 부산·청주·대구·제주·무안은 각각 분리한다.
- 모든 조합은 하나의 대기열, 14일 TTL, 일반 회차당 최대 5개 갱신이다.
- 현재 받는 `avg`와 `lowest`는 월별 비교 근거이며, 빠른 출발 카드 가격을 다시 넣어 중복 계산하지 않는다.
- 기준가가 아직 없는 조합은 제거하거나 감점하지 않는다.

- 현재 가격과 같은 날짜 비교가만 보지 않고 노선 가격 흐름을 나중에 검증할 수 있도록 기록을 쌓는다.
- `flight_price_daily`, `route_price_daily`의 의미와 보관은 `docs/long-term-price-history.md`를 따른다.
- 과거 가격 데이터가 있다는 이유만으로 바로 공개 배지나 강한 판정에 사용하지 않는다.
- 표본 수, 기간, 수집 실패 여부를 함께 확인한 뒤 제품에 적용한다.

## Hermes 원격 땡처리 실행자

브랜치 `codex/ttang-browser-runner`, 커밋 `b89760ca`에 구현돼 있다.

- `npm run hermes:ttang:enroll`: 해당 PC를 전용 실행 호스트로 등록
- `npm run hermes:ttang:status`: 등록·Chrome·잠금·정책 상태 확인
- `npm run hermes:ttang:pilot`: staging 파일럿 1회
- `npm run hermes:ttang:scheduled`: 기존 대체 수집 정책을 통과할 때만 staging 실행

안전장치:

- 등록된 PC에서만 실행
- `127.0.0.1:9222`의 보이는 Chrome만 사용
- 동시 실행 잠금
- 운영 데이터 파일 해시가 바뀌면 실패
- 자동 병합·커밋·푸시·배포 없음
- 실패 자동 재시도 없음

이 브랜치는 아직 `main`과 운영에 반영되지 않았다. 메인에 합치기 전 최신 `origin/main`을 반영하고
크롤러 PC에서 파일럿 성공과 staging 요약을 검증한다.

## 크롤러 PC 봇의 실행 경계

크롤러 PC 봇은 다음만 한다.

1. 상태 확인
2. 메인 Hermes가 지정한 모드의 단일 실행
3. summary·crawl log·첫 구조 오류를 반환
4. Chrome과 프로세스 종료 상태 확인

다음은 하지 않는다.

- 운영 캐시 병합
- 데이터 커밋·푸시
- Vercel 배포
- 정책을 우회한 재실행
- 로그인 정보·쿠키 출력
- 수집 실패를 판매 종료로 판정
