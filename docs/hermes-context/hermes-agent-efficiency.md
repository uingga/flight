# Hermes Agent 작업 효율 원칙

> 적용 범위: 티키티킷에서 작업하는 Hermes Agent(보리스·샘·티보)
>
> 이 문서는 Hermes 전용 운영 원칙이다. Codex·Claude Code의 작업 방식과 `xhigh` 설정을 변경하지 않으며, 공용 지침인 `AGENTS.md`에도 이 원칙을 복제하지 않는다.

## 목적

Hermes의 스킬·메모리·도구 활용과 안전 검증은 유지하되, 작업 효과와 무관한 위임·재검사·의식적인 절차를 줄인다. 세 Hermes 봇은 공통 효율 원칙을 공유하지만 역할별 검증 방법은 다르게 적용한다.

## 기본 원칙

1. **경계는 공유하고 내부 절차는 강제하지 않는다.** 운영 데이터 보호, 비밀정보 보호, 배포 권한, 완료 주장에 필요한 근거, 결과 보고 기준은 공유한다. TDD 여부, 서브에이전트 수, 계획 형식, 내부 추론 과정, 동일한 테스트 명령은 모든 역할에 일괄 적용하지 않는다.
2. **Hermes의 강점은 선택적으로 사용한다.** 관련 스킬과 프로젝트 문맥을 먼저 확인하되, 가능한 모든 스킬·도구·서브에이전트를 사용하는 것을 목표로 삼지 않는다. 기계적인 단일 작업은 담당 봇이 직접 처리한다.
3. **위임은 독립성과 효과가 있을 때만 한다.** 서로 독립적인 조사나 전문 검토를 병렬화하면 시간 또는 품질 이득이 분명할 때만 역할별로 나눈다. 여러 에이전트에게 같은 무차별 검토를 반복시키지 않으며, 최종 판단과 완료 보고의 책임자는 한 명으로 둔다.
4. **검증 강도는 위험에 맞춘다.** 낮은 위험은 관련된 좁은 확인 한 번, 중간 위험은 관련 확인과 안정화 뒤 최종 타입 검사·빌드·통합 확인, 높은 위험은 관련 확인과 최종 전체 검증에 더해 실제로 위험을 줄일 수 있는 독립 검토를 적용한다. 운영 데이터·인증·권한·결제·파괴적 작업·외부 서비스 차단 위험은 높은 위험으로 본다.
5. **작업 중에는 좁게, 안정화 뒤에는 넓게 검증한다.** 수정 중에는 현재 변경을 가장 빨리 반증할 수 있는 표적 검사를 사용한다. 코드와 문서가 안정된 뒤 전체 테스트·빌드·리뷰를 필요한 범위에서 한 번 실행한다. 같은 전체 검사를 이유 없이 반복하지 않는다.
6. **최종 검토에서 결함이 나오면 영향 범위만 다시 검증한다.** 결함을 고친 뒤 직접 관련된 검사를 실행하고, 그 수정으로 무효화된 최종 검사만 다시 실행한다. 검토 대상 동작이 실질적으로 바뀐 경우에만 독립 검토를 다시 요청한다.
7. **역할별 검증은 다르게 한다.** 코딩은 테스트·타입·빌드, 데이터 운영은 staging·건수·신선도·운영 데이터 보존, 조사는 출처 교차 확인, 문서는 사실·문체 확인을 중심으로 한다.
8. **`xhigh`는 설정이지 방법론이 아니다.** 사용자가 선택한 추론 강도는 유지한다. 이를 Hermes의 고유 방식으로 설명하거나 검토 횟수·서브에이전트 수를 늘리는 근거로 사용하지 않는다. 속도를 설명할 때는 모델 설정, 도구 비용, 프로젝트 안전 요구, 담당 봇이 선택한 절차를 구분한다.
9. **안전과 외부 상태 확인은 줄이지 않는다.** 비밀정보·운영 데이터·배포 경계를 지키고, 외부 시스템을 변경한 뒤에는 정확한 대상을 다시 읽어 실제 반영을 확인한다. 효율화를 이유로 필요한 안전장치나 완료 근거를 생략하지 않는다.

## 티키티킷 적용 순서

1. 현재 대화의 최신 지시와 `HERMES_START_HERE.md`를 확인한다.
2. 작업에 필요한 `docs/hermes-context/` 문서만 읽고, 설명을 실제 코드·데이터·운영 상태와 대조한다.
3. 변경을 운영 수정, 실험, 문서화, 데이터 갱신 중 하나로 분류하고 위험도를 정한다.
4. 구현 중에는 표적 검사만 실행한다.
5. 변경이 안정되면 위험도와 역할에 맞는 최종 검사·빌드·리뷰를 필요한 범위에서 한 번 실행한다.
6. 커밋·푸시·배포·운영 반영은 사용자가 허용한 범위까지만 수행하고, 외부 변경은 읽어 확인한다.

## 완료 보고

완료 보고에는 다음을 짧고 명확하게 적는다.

- 무엇을 변경했는지
- 실제로 무엇을 검증했는지
- 아직 실행하지 않았거나 남아 있는 것이 무엇인지
- 외부 상태나 운영 상태가 바뀌었는지

코드 수정, 샘플 검증, 전체 규모 수집, staging, 운영 반영, 커밋, 푸시, 배포를 서로 구분한다. 명령이 성공했다는 사실만으로 운영 반영이나 외부 상태 변경이 완료됐다고 주장하지 않는다.
