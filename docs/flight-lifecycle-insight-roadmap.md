# 항공권 생애 기록과 데이터 인사이트 실행 계획

## 결정 상태

- 방향 확정: 2026-08-24
- `tracking_started_at`: 2026-08-25 (KST, 첫 운영 기록 성공일)
- 구현 상태: 기록기·자동 실행·운영 DB 누적 정상. 추천 판정에는 아직 사용하지 않음
- 미리보기 상태: 단일 사건형 인사이트바 구현 완료, 개별 항공권 이력 연결 전에는 노선 최저가 기준으로 제한
- 원칙: 예측 기능보다 관측 데이터의 신뢰성을 먼저 확보한다.
- 원칙: 충분한 표본이 없는 통계와 과장된 품절 표현은 공개하지 않는다.
- 현재 결정: 노선 가격 흐름은 데이터만 누적하고, 가격 이중 검증과 추천 반영은 표본 검토 뒤 별도로 결정한다.

## 목표

티키티킷이 항공권을 현재 목록의 한 행이 아니라, 최초 발견부터 가격·좌석 변화와 일시 중단·재등장·판매 종료까지 이어지는 하나의 생애로 기록한다.

이 데이터로 사용자가 다음 질문에 답을 얻도록 한다.

- 이 표의 가격은 실제로 내려갔는가?
- 처음 발견됐을 때보다 좌석이 얼마나 줄었는가?
- 잠시 사라졌다가 다시 판매된 표인가?
- 비슷한 땡처리표와 비교해 지금 가격은 어느 정도인가?
- 충분한 근거가 쌓였을 때 기다리는 편과 사는 편 중 어느 쪽이 나은가?

## 현재 확인된 한계

- `flight_price_daily`는 같은 날의 마지막 상태만 남겨 하루 중 변화를 보존하지 못한다.
- 일부 여행사의 항공권 ID에 가격이 들어가 가격 변경을 새 항공권으로 판단할 수 있다.
- 현재 `price-history.json`은 개별 항공권이 아닌 노선별 일일 최저가·평균가 기록이다.
- 한 항공권이 사라지거나 재등장한 사건을 별도로 기록하지 않는다.
- 여행사 수집 실패와 개별 항공권 판매 종료를 구분하는 생애 상태가 없다.
- 좌석 수는 정확한 수, `9석 이상`, 정보 없음, 확인 실패를 구분하지 않는다.
- 네이버 비교가는 현재 직항과 경유가 섞일 수 있어 엄격한 가격 판단 기준으로 사용하기 어렵다.

## 1단계 — 기록 기반 만들기

기록 시작일을 만드는 가장 먼저 할 작업이다. 화면은 바꾸지 않고 내부 기록부터 시작한다.

1. 가격을 제외한 `offer_key`와 여정 단위 `itinerary_key`를 정의한다.
2. 여행사 상품번호가 바뀌어도 같은 여정 후보를 연결할 수 있게 한다.
3. 현재 상태를 저장하는 `offer_current`를 만든다.
4. 최초 발견, 가격 변경, 좌석 변경, 일시 미확인, 재등장, 판매 종료를 저장하는 `offer_events`를 만든다.
5. 각 여행사의 수집 성공·실패·보존 여부를 기록하는 `crawl_runs`와 연결한다.
6. 기존 일별 가격 테이블은 장기 통계용으로 유지한다.
7. 전체 크롤과 마이리얼트립 별도 갱신 모두 같은 생애 기록기를 거치게 한다.

### 구현된 안전장치

- 가격이 ID에 들어가는 여행사도 가격 변경 전후를 같은 판매 회차로 잇는다.
- 마이리얼트립은 오는 날짜·항공사·출도착 시각이 달라지면 다른 항공권으로 구분한다.
- 수집 실패와 이전 데이터 보존 회차는 사라짐 판정에서 제외한다.
- 원본 수집량이 직전보다 15% 넘게 줄어든 회차는 확인된 가격·좌석만 기록하고, 안 보인 표는 사라진 것으로 세지 않는다.
- 마이리얼트립 일부 조회가 실패한 회차도 같은 방식으로 안 보인 표를 사라진 것으로 세지 않는다.
- 마이리얼트립의 `9석`은 정확히 9석이 아니라 `9석 이상`일 수 있는 값으로 구분해 저장한다.
- 같은 공항·같은 날짜로 확인된 네이버 비교가와 확인 시각도 값이 있는 항공권에 한해 함께 저장한다. 비교가가 없는 회차가 과거 값을 삭제하지 않으며, 직항 여부가 확실하지 않아 당분간 공개 판단 문구에는 쓰지 않는다.
- 네이버만 확인한 회차는 여행사 재고를 다시 본 것이 아니므로 `마지막 발견` 시각이나 판매 종료 판정을 갱신하지 않는다.

### 상태 판정 초안

- 정상 수집에서 1회 미확인: `missing_once`
- 정상 수집에서 3회 연속 미확인: `paused_estimated`
- 72시간 안에 같은 상품 또는 높은 신뢰도의 같은 여정 재등장: `reappeared`
- 72시간 초과 또는 출발일 경과: `ended_estimated`
- 수집 실패·수집량 이상·이전 데이터 보존 회차: 미확인 횟수에 포함하지 않음

위 숫자는 첫 2주 관측 결과로 조정한다.

## 2단계 — 인사이트바 개편

공개 미리보기에서 먼저 검증하고, 메인 반영은 별도 결정한다.

현재 적용 위치는 `/preview/mobile-redesign`뿐이며 운영 메인에는 적용하지 않는다.

### 구성 원칙

- 인사이트바 하나에는 한 가지 사건과 한 항공권만 보여준다.
- 첫 16개 카드 안에는 최대 두 개만 보여준다.
- 전체 탐색 흐름에는 최대 5개만 보여준다. 상한 구성은 `가격·기록 2 + 일정·기회 2 + 여행지 발견 1`이다.
- 배경은 흰색을 유지하고 변화 숫자와 행동 요소에만 브랜드 색을 쓴다.
- 보여줄 만한 변화가 없으면 억지로 인사이트바를 만들지 않는다.
- 완성형 광고 문장 대신 `🚨 가격 붕괴 감지`, `🏃 0연차 탈출 가능`처럼 짧은 사건 라벨을 제목으로 쓴다.
- 같은 목적지·같은 종류는 한 번씩만, 강한 경보형 제목은 한 화면에 하나만 쓴다.
- 같은 항공권의 변화가 확인되지 않은 동안에는 `항공권 가격`이 아니라 `노선 최저가` 변화라고 표현한다.
- 인사이트 클릭은 가격 변화·여행지 발견·지금 가능한 여행·새 노선으로 나눠 측정한다.

### 우선순위

1. 검증된 가격 하락·좌석 변화·재등장
2. 오늘 처음 발견한 표
3. 지금 가능한 여행
4. 티키티킷 데이터 분석
5. 여행지 발견

### 문구 예시

```text
🚨 가격 붕괴 감지
오사카 · 171,000원 → 129,000원
42,000원 내림
```

개별 항공권 기록 전에는 다음처럼 제한한다.

```text
💸 4.2만원 증발
오사카 노선 최저가
171,000원 → 129,000원
```

여행지 발견은 가격 사건과 일정 인사이트 사이에 최대 하나만 섞는다.

```text
🧭 요나고 입문
일본 산인 지방의 관문으로, 가이케온천·사카이미나토·마쓰에를 함께 둘러보기 좋은 거점
```

데이터 분석형 인사이트 예시:

```text
티키티킷 데이터
후쿠오카 항공권, 얼마면 잘 샀다고 할 수 있을까요?
지난 6개월 땡처리표 분석 보기
```

## 데이터 축적 뒤 점검 일정

모든 기간은 1단계가 운영에 배포되어 `tracking_started_at`이 기록된 날부터 계산한다.

### 2주 후

- 상품 연결과 재등장 판정 오차를 표본 검토한다.
- 가격 변경이 새 항공권으로 잡히는 비율을 확인한다.
- 수집 실패가 판매 종료로 잘못 기록되지 않았는지 확인한다.
- 좌석 정보 제공 범위와 정확한 수·하한 표시를 여행사별로 정리한다.
- 상태 판정의 3회·72시간 기준을 조정한다.

### 1개월 후

- 검증된 가격 하락, 좌석 변화, 재등장 인사이트를 미리보기에 연결한다.
- 인사이트 노출, 상세 열람, 여행사 예약 클릭을 함께 측정한다.
- 최소 표본을 충족한 노선만 `최근 관측 가격` 문구를 사용한다.

### 3개월 후

- 출발 D-day별 가격 분포를 시험 분석한다.
- 고유 항공권 수, 판매 회차 수, 전체 관측 횟수를 분리해 집계한다.
- 후쿠오카·오사카·도쿄처럼 표본이 큰 노선부터 데이터 글을 만든다.
- 좌석 감소 뒤 판매 종료까지 걸린 시간을 분석하되 예측 문구는 아직 제한한다.

### 6개월 후

- `후쿠오카 항공권은 얼마면 사도 괜찮을까?` 같은 상시 데이터 페이지를 검토한다.
- `출발 며칠 전에 가격이 가장 많이 떨어졌나?`를 노선·시기·직항·여행 기간별로 분석한다.
- `10만원 이하 도쿄 항공권은 몇 번 나왔나?`를 판매 회차 기준으로 집계한다.
- 연말에는 `올해 가장 크게 떨어진 항공권 TOP 20` 콘텐츠를 검토한다.
- 충분한 표본이 있는 구간에만 `기다릴까, 살까` 실험을 검토한다.

## 공개 통계의 최소 기준

- 관측 횟수가 아니라 고유 상품 또는 판매 회차를 기본 단위로 쓴다.
- 분석 기간과 표본 수를 항상 함께 표시한다.
- 출발지, 목적지, 직항 여부, 출발 시기, 여행 기간, 수수료 포함 여부를 맞춘다.
- 특정 상품이 오래 살아남아 통계를 과도하게 지배하지 않도록 상품·일 단위 가중치를 검토한다.
- 수집 실패, 보존 데이터, 형식 불일치 회차는 판매 종료와 가격 변화 분석에서 제외한다.
- 표본이 부족하면 숫자를 공개하지 않고 더 기다린다.

## 자동 점검 원칙

- 매주 이 문서를 확인한다.
- 1단계가 시작되지 않았으면 시작 지연을 한 번 알리고, 같은 내용으로 반복 알림하지 않는다.
- `tracking_started_at`이 생긴 뒤에는 2주·1개월·3개월·6개월 시점에만 사용자에게 다음 단계와 근거를 알린다.
- 시점이 됐더라도 표본이나 데이터 품질이 부족하면 부족한 이유와 다시 확인할 조건을 알린다.
- 자동 점검은 크롤링을 실행하거나 코드를 배포하지 않고 기록 상태만 읽는다.
