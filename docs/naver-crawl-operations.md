# 네이버 가격 확인 운영

## 실행 분담

| 실행 위치 | 시각·조건 | 대상 | 최대 건수 | 역할 |
|---|---|---:|---:|---|
| GitHub Actions | 수동 진단만 | `myrealtrip` | 3 | 클라우드 접속 상태 확인(운영 반영 없음) |
| Windows `TikitikitNaverCrawl` | 11:12 1차, 14:23 실패 소스 보완, 17:31 시작 안전망 | 정상 수집된 여행사 | 하루 합산 200 | 주거용 회선의 유일한 운영 네이버 수집 |

GitHub 호스팅 러너에서는 HTTP와 일부 GraphQL이 정상이어도 실제 운임 화면만 계속 로딩되는
soft block이 반복됐다. 같은 코드로 2026-08-28 GitHub는 5/176건, Windows는 278/280건이
성공해 트리거가 아니라 데이터센터 실행 환경이 주원인으로 확인됐다. 과거에는 조기 중단 회차도
워크플로가 초록색으로 표시돼 최근부터 갑자기 실패한 것처럼 보인 구간도 있었다.

따라서 `myrealtrip-scrape.yml`을 포함한 어떤 GitHub 워크플로도 `naver-crawl.yml`을 자동 호출하지
않는다. 이 워크플로는 선택 입력을 1건 또는 3건으로 제한하고 대조 조회도 같은 페이지 이동
예산에 포함한다. 동시 실행을 직렬화하고 실제 요청을 보낸 진단 뒤 24시간 동안 새 진단을
거절한다. 같은 실행의 재실행도 이전 시도의 실제 요청 시각을 확인한다. `contents: read`와
실행 이력 확인용 `actions: read`만 부여하며 가격·필터·실행 이력을 커밋하지 않는 수동 진단 전용이다.

`daily-crawl.yml`의 11:12 일반 크롤은 GitHub 네이버 워크플로를 호출하지 않는다. 일반 여행사
수집만 수행하고 오늘의 표를 새로 뽑지는 않는다. 오늘의 표는 PC 네이버 수집의 당일 단계가
모두 끝나고 가격이 운영 API에 반영된 뒤 하루 한 번만 선정한다. 일부 여행사가 실패한 날은
그날 정상 수집된 소스만 후보로 사용한다. 별도 `today-pick.yml`은 수동 실행 전용이다.

## Windows 실행과 오늘의 표 선정

Windows 작업은 `scripts/install-naver-crawl-task.ps1`이 11:12·14:23·17:31 KST로 등록한다.
11:12 일반 여행사 크롤이 반영되면 그 회차에서 정상 수집된 소스와 당시 최신 마이리얼트립을
먼저 확인한다. 실패해 이전 캐시를 유지한 소스의 예상 후보 비율만큼 일일 예산을 남기고,
14:23 회차에서 실제로 복구된 소스만 두 번째로 확인한다. 14:23에도 복구되지 않은 소스는
그날 네이버 비교와 오늘의 표 후보에서 제외한다. 17:31 트리거는 앞 작업이 기동되지 못했을 때의
시작 안전망일 뿐 별도 세 번째 예산을 만들지 않는다. 각 단계 완료 감지 뒤 30~180초의 짧은
무작위 지연을 두며, 대기 확인 과정에서는 네이버 페이지를 열지 않는다. 20:30 폴백은 사용하지 않는다.

주거용 IP에서 단계별 소스 필터를 적용하고, 상태 파일에 누적 이동량을 저장해 두 단계를 합친
페이지 이동 하드캡을 200회로 제한한다. 각 검색은 최소 10초를
기다리고, 화면 로딩이 끝난 뒤 최저가가 4초 동안 변하지 않으면 다음 항공권으로 넘어가며 늦는
페이지도 최대 25초까지만 기다린다. 검색 사이 5~10초, 10건마다 60~120초를 추가로 쉬는 차단
보호 간격은 유지한다. 대조 노선 확인도 200회 예산 안에서 회차당 한 번으로 제한한다.
마지막 성공 뒤 실제 24시간 동안은 여행사 가격이 바뀌어도 같은 키를 다시 요청하지 않고,
변경 없는 키는 통상 2일 간격으로 확인한다. 403/429/CAPTCHA
등 명시적 제한이면 즉시 중단하고 같은 KST 날짜에는 다시 실행하지 않는다. 정확히 24시간을
계산하지 않고 다음 날 정규 네이버 회차에서 한 번 재탐색해, 실행 시각 차이 때문에 다음 날까지
통째로 건너뛰지 않게 한다. 명시적 접근 제한 뒤에는 같은 날 14:23 보완 단계와 Task Scheduler
자동 재시작을 모두 허용하지 않는다.

시스템성 일시 오류는 명시적 차단과 구분한다. 진행 가격과 위치를 체크포인트로 저장하고 10~20분
무작위로 한 번 쉰 뒤, 실패한 항공권을 즉시 반복하지 않고 그 다음 항공권부터 같은 프로세스에서
이어간다. 휴식 전후의 네이버 페이지 이동을 합쳐 하루 200회 상한을 유지한다. 재개 뒤에도 시스템성
오류가 이어져 조기 종료되면 그때까지 성공한 가격은 운영 데이터에 병합·필터링하되, 불완전 회차로
오늘의 표를 새로 선정하지 않는다. 성공 가격이 0건이거나 명시적 차단이면 가격은 반영하지 않는다.
브라우저 실행·대기열 준비처럼 실행 상태 파일상 네이버 요청이 0건인 단계에서 실패한 경우에만
15~30분 무작위로 쉰 뒤 전체 프로세스를 한 번 재시도한다. 요청이 한 건이라도 시작됐거나 실행
상태를 확인할 수 없으면 이 재시도를 허용하지 않는다.

일반 여행사 크롤도 HTTP 상태만 보지 않는다. HTTP 200 응답 안의 CAPTCHA·WAF·비정상 접근
안내와, 이전 정상 원본 대비 0건 또는 60% 미만으로 줄어든 응답을 soft block 의심으로 판정한다.
의심 결과는 캐시에 반영하지 않고 이전 데이터를 유지하며, 해당 여행사는 24시간 뒤 단일
재탐색 시점까지 자동 요청을 멈춘다.

## 일반 여행사 PC 대체 수집

`TikitikitBlockedSourceCrawl` 작업은 일반 크롤과 같은 08:17·11:12·14:23·17:31 KST에
시작하고, 각 GitHub 회차가 `main`에 반영될 때까지 사이트 요청 없이 대기한다. 반영된 캐시에
유효한 차단 회로가 있을 때만 해당 여행사를 골라 `%USERPROFILE%\Tikitikit\source-fallback-crawler`
전용 체크아웃에서 부분 크롤한다. 차단되지 않은 여행사에는 PC 요청을 보내지 않는다.
PC 자동 대체 대상은 여행사별 GitHub 실패 회차를 기준으로 퐁당퐁당 실행한다. 실패한 회차는
PC가 즉시 대체하고, 다음 일반 회차는 해당 여행사에 접속하지 않으며, 그다음 회차는 다시 PC가
수집한다. 이 수집/휴식 교대는 GitHub 차단 회로가 열린 24시간 동안 유지한다. 여행사마다 실패
회차가 다르면 같은 시각에도 PC 수집 여부를 각각 따로 판정한다. 모두투어는 이 규칙의 대상이 아니다.
땡처리닷컴은 이 작업이 네 회차 모두 기동되더라도 08:17·14:23 회차에만 PC 대체 후보가 된다.
같은 KST 날짜 앞 허용 회차에서 이미 PC 대체에 성공했거나 PC 차단 휴식 중이면 다시 요청하지 않는다.

PC 수집이 성공해도 GitHub 실행 환경의 24시간 차단 회로는 그대로 유지한다. 따라서 휴식 기간에는
PC 결과만 소스 단위로 최신 원격 캐시에 병합되고, 24시간 뒤 GitHub가 단일 재탐색한다. PC에서도
403·429·CAPTCHA·0건·급감이 확인되면 PC 대체 수집만 별도로 24시간 멈춘다. 작업 설치·갱신은
`scripts/install-source-fallback-task.ps1`로 수행한다.

Task Scheduler의 `IgnoreNew`와 별도로 named mutex를 사용하므로 예약 실행 중 수동 실행도
겹치지 않는다. 작업은 네트워크 연결을 요구하고 PC를 깨우며, 대기 시간을 포함해 최대 12시간 뒤 종료된다. 브라우저가
실제 화면을 사용하므로 Windows 사용자 세션은 로그인 상태여야 한다.

이 PC의 Task Scheduler는 `%LOCALAPPDATA%` 아래 PowerShell 스크립트를 `0xFFFD0000`으로
거부하고, Dropbox 개발 폴더는 실행 중인 Next.js 바이너리와 `npm ci`가 충돌할 수 있다. 설치
스크립트는 `%USERPROFILE%\Tikitikit\naver-crawler`에 깨끗한 전용 체크아웃을 만들고 그 경로만
작업 대상으로 등록한다. 실행기는 자동 `git pull --rebase --autostash origin main`과 경로 제한
커밋으로 최신 데이터를 병합한다.

성공한 가격은 최신 원격 네이버 데이터와 병합하고 최신 항공권 캐시를 다시 필터링해 커밋한다.

검색 대상은 오래된 네이버 값을 제외한 임시 추천순으로 정한다. 7일 이상 밀린 키를 먼저 강제
승격하고, 신규·실결제가 변경 추천 상위, 나머지 추천 상위 50개, 추천 중간, 추천 하위 순으로
하루 최대 200개를 선택한다. 여행사 실결제가가 1만원 이상 또는 3% 이상 달라졌을 때만 가격
변경으로 취급한다. 미선택 키는 최초 대기 시각과 함께 보존해 다음 회차로 넘긴다.
실제 요청 스크립트는 `NAVER_LIVE_RUN=1`이 없으면 브라우저를 열지 않으므로 예약 실행기를
우회한 실수성 직접 실행도 차단한다.
매 정규 조회에서 판매처 표시 가능성을 패시브로 진단한다. 이미 로드된 GraphQL·DOM의
판매처 필드와 최저가 행의 문맥만 기록하며, 편을 펼치거나 예약처를 클릭하거나 추가 요청을
보내지 않는다. 판매처가 최저가와 안정적으로 연결되는지 확인되기 전에는 운영 항공권 데이터에
반영하지 않는다.
네이버 가격은 마지막 성공 후 24시간까지만 추천 보정·비교 문구·비싼 항공권 제거에 사용하고,
그 이후에는 원본 기록만 보존한 채 새 확인 전까지 화면 판단에서 제외한다.

네이버 수집·필터링 데이터가 `main`에 반영되고 운영 항공권 API가 해당 캐시 이상으로 올라온
뒤에만 `node scripts/select-today-pick.mjs`를 실행해 하루 한 번 새 표를 선정한다. 11:12 1차에서
실패 소스가 있으면 선정을 14:23 보완 뒤까지 미루고, 소스 필터를 전달해 이전 캐시를 보존한
여행사가 후보에 섞이지 않게 한다. 변경된 `data/today-pick.json`만 별도 커밋한다.

동시에 다른 데이터 커밋이 들어와 push가 거절되면 로컬 선정 커밋을 되돌리고 최신 `main`과
운영 API를 다시 받은 뒤 신규 선정을 재실행한다. 두 번 모두 반영하지 못하면 오류로 종료하고
낡은 선정 결과를 강제로 밀어 넣지 않는다.
